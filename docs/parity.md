# Legacy parity baseline

## Purpose

This matrix tracks intended compatibility with `lit-analyzer`, `ts-lit-plugin`, and the `lit-plugin` editor experience. It does not claim that the TS7 implementation already provides these capabilities.

Statuses:

- **verified** — the legacy result and fixture are reproducible in this repository.
- **partially verified** — a local or pinned upstream fixture exists and runs, but not every aspect of the capability is covered.
- **upstream reference** — no local fixture exists; the pinned upstream test is the only evidence.
- **pending** — coverage is missing: no verified fixture exists yet. This means missing coverage, not planned TS7 functionality.
- **implemented** — the TS7 implementation has its own verified result; none currently has this status.

A verified legacy result is not automatically the desired TS7 behavior. Intentional corrections require TypeScript or Lit semantics and regression fixtures.

## Reproducible baseline

- `lit-analyzer`: 2.0.3
- `ts-lit-plugin`: 2.0.2
- TypeScript used by the legacy fixture: 5.2.2
- Lit used by the fixture: 3.3.2
- Source snapshot used to audit rule IDs and behavior: `runem/lit-analyzer` revision `a518bf7c84ac338a7e8ab3db9dad006c06144426` (2025-08-04).

The isolated fixture in `tests/fixtures/legacy/` has its own manifest and lockfile, so legacy TypeScript does not mix with the workspace's TypeScript 7 installation. It is outside the pnpm workspace. Upstream test cases and assertions are preserved under `src/test/` and run directly as TypeScript with Node 26 and `node:test`, without AVA or a compilation step. Each scenario is materialized with its source files and `tsconfig.json` into the ignored `.test-projects/` directory, allowing both legacy and future TS7 providers to analyze the same on-disk project. The suite covers 162 passing diagnostics and code-fix scenarios and 3 upstream skips using the latest supported legacy TypeScript version, 5.2.2. Parser and indexer tests that inspect legacy-specific compiler models are referenced from the pinned revision rather than copied.

Run the complete baseline with `pnpm test:baseline`, or include it with all other checks through `pnpm test`. These commands install the fixture with its frozen lockfile before running the Node.js tests. The scenario harness selects its implementation through `ANALYZER_PROVIDER`, which defaults to `legacy`; `src/test/helpers/legacy-provider.ts` creates the published legacy analyzer. Shared scenario contracts for configuration, ranges, diagnostics, and code fixes belong to `packages/analyzer` rather than the legacy fixture. A future TS7 provider can be added behind the same boundary without changing scenario assertions. A passing legacy suite alone does not prove TS7 correctness. To run only the legacy CLI example:

```sh
cd tests/fixtures/legacy
pnpm install --frozen-lockfile
./node_modules/.bin/lit-analyzer src/incompatible-type-binding.ts --strict --format list --noColor
```

The expected result is one `no-incompatible-type-binding` error at line 6, column 3 and exit code 1. The valid binding on line 4 produces no diagnostic.

### Rule coverage gaps

Five rules have no executable fixture coverage. The reasons were verified against the pinned source snapshot and the published `lit-analyzer` 2.0.3 package:

- `no-invalid-attribute-name` — the rule is implemented and registered in [`ALL_RULES`](https://github.com/runem/lit-analyzer/blob/a518bf7c84ac338a7e8ab3db9dad006c06144426/packages/lit-analyzer/src/lib/rules/all-rules.ts) with severity `["error", "error"]` at the pinned revision, but upstream ships no rule test for it and none was written locally. Status: `no upstream fixture`, `pending`.
- `no-invalid-tag-name` — same situation: implemented and registered upstream, severity `["error", "error"]`, with no upstream rule test. Status: `no upstream fixture`, `pending`.
- `no-invalid-css` — this ID is not a rule module at all. It is declared in [`DEFAULT_RULES_SEVERITY`](https://github.com/runem/lit-analyzer/blob/a518bf7c84ac338a7e8ab3db9dad006c06144426/packages/lit-analyzer/src/lib/analyze/lit-analyzer-config.ts) with severity `["warn", "error"]`, and CSS diagnostics are emitted directly by the CSS language service wrapper with `source: "no-invalid-css"`. No upstream test exercises the CSS diagnostics pipeline. Status: `no upstream fixture`, `pending`.
- `no-expressionless-property-binding` — the rule is implemented and registered in `ALL_RULES` with severity `["error", "error"]` at the pinned revision and is documented in the upstream README, but upstream ships no rule test for it and none was written locally. Status: `no upstream fixture`, `pending`.
- `no-invalid-boolean-binding` — the rule ID and default severity `["error", "error"]` are declared in `DEFAULT_RULES_SEVERITY` and the ID is documented in the upstream README, but no rule module with this ID is registered in `ALL_RULES` at the pinned revision, and the published 2.0.3 package contains no such rule under `lib/rules/`. The upstream test file exists with all three scenarios marked `skip`, and the local copy at `src/test/rules/no-invalid-boolean-binding.test.ts` preserves those three skips. The rule ID and scenarios exist; the legacy implementation is absent, so the local baseline records 3 skips and no passes for this rule.

## Legacy accuracy audit

Scope: the 162 passing scenarios and 3 skips in the local baseline (`pnpm test:baseline`, TypeScript 5.2.2), plus the pinned upstream rule, parser, and indexer tests at revision `a518bf7c84ac338a7e8ab3db9dad006c06144426`. Each scenario's asserted diagnostics were compared with the behavior the rule IDs and TypeScript/Lit semantics imply, and the pinned upstream tests were reviewed for skipped or contradicting assertions.

Evidenced discrepancy:

- **False negative — `no-invalid-boolean-binding` (legacy).** The rule is declared with severity `error`/`error` and documented upstream, but legacy never emits this rule ID: the pinned source registers no module for it in `ALL_RULES`, the published 2.0.3 package contains no such rule, and the pinned upstream test file keeps all three scenarios skipped. Concretely, the template `` html`<input ?type="${true}" />` `` produces only a `no-incompatible-type-binding` diagnostic (message: "You are using a boolean binding on a non boolean type ..."), emitted through the shared `is-assignable-in-boolean-binding` utility, and never a `no-invalid-boolean-binding` diagnostic. The skipped upstream scenarios encode the expected behavior: flag a boolean binding on a non-boolean type, stay silent on a boolean type, and respect `rules: {"no-invalid-boolean-binding": "off"}`. Evidence: [pinned upstream test](https://github.com/runem/lit-analyzer/blob/a518bf7c84ac338a7e8ab3db9dad006c06144426/packages/lit-analyzer/src/test/rules/no-invalid-boolean-binding.ts), [pinned `ALL_RULES`](https://github.com/runem/lit-analyzer/blob/a518bf7c84ac338a7e8ab3db9dad006c06144426/packages/lit-analyzer/src/lib/rules/all-rules.ts), [pinned `DEFAULT_RULES_SEVERITY`](https://github.com/runem/lit-analyzer/blob/a518bf7c84ac338a7e8ab3db9dad006c06144426/packages/lit-analyzer/src/lib/analyze/lit-analyzer-config.ts).

Scoped no-findings result: within the audit scope above, no other evidenced false positive or false negative was identified among the rules that have passing baseline scenarios. This is a scoped result, not a claim that none exist. Remaining uncertainty:

- The upstream GitHub issue tracker, which reports additional legacy inaccuracies, was not audited; only the pinned source and tests were.
- Editor, CLI project-selection, source-map, manifest, and CSS-diagnostics features have no fixtures (see the feature matrix), so their accuracy is unaudited.
- Only legacy TypeScript 5.2.2 was exercised; other compiler versions may differ.
- No fuzzing or adversarial template corpus was run; the audit covers the existing scenario assertions.
- The `no-incompatible-type-binding` fixture setup carries an upstream TODO noting a `ts-simple-type` bug workaround (a removed generic in the test double). It affects fixture scaffolding, not an asserted diagnostic, so it is not recorded as a discrepancy.
